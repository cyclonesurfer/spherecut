# Slice 5b: zero-copy decode to render

The M1 plan's item 2 and item 9 (section 0, D25) as designed on
2026-10-30, after slice 7. Two paths are built and measured, and the copy
path stays the default until the decision before M3 (D25).

- **A, DMA-BUF import.** VA-API decodes; each frame is mapped to DRM
  PRIME and its planes are imported into wgpu's device as textures.
- **B, one shared device.** wgpu's own Vulkan device is handed to
  FFmpeg's Vulkan hwcontext, so Vulkan Video decodes into images wgpu
  can sample.

odin's numbers (PR #3) make both worth having: on its discrete RX 7600
VA-API with its CPU copy is 0.81 to 1.29 × real time on the X5 modes, and
Vulkan Video with the copy 1.61 to 2.23 ×. The copy is the cost both
paths take away.

## What the APIs give (checked in the registry sources)

- wgpu-hal 30.0.1 has `vulkan::Device::texture_from_dmabuf_fd(fd, desc,
  drm_modifier, stride, offset)`: a **single-plane** import, with
  `VK_IMAGE_TILING_DRM_FORMAT_MODIFIER_EXT`, one explicit plane layout
  and a dedicated `VkDeviceMemory` from the fd. Vulkan takes the fd on
  success, and it is closed on failure. It needs
  `Features::VULKAN_EXTERNAL_MEMORY_DMA_BUF`, which wgpu offers when the
  adapter has `VK_EXT_external_memory_dma_buf` and
  `VK_EXT_image_drm_format_modifier`. `Device::create_texture_from_hal`
  wraps the result for wgpu.
- wgpu-hal 30's `vulkan::Adapter::open_with_callback` lets the caller add
  device extensions, features and queue create infos before
  `vkCreateDevice`, and `wgpu::Adapter::create_device_from_hal` wraps
  the result. That is path B's device.
- FFmpeg 8.1's `vaapi_map_to_drm_esh` (`av_hwframe_map` to
  `AV_PIX_FMT_DRM_PRIME` with `AV_HWFRAME_MAP_READ`) calls
  `vaSyncSurface` and then `vaExportSurfaceHandle` with
  `VA_EXPORT_SURFACE_SEPARATE_LAYERS | VA_EXPORT_SURFACE_READ_ONLY`. So
  the decode is done when the map returns, and NV12 comes as two layers
  (`DRM_FORMAT_R8` and `DRM_FORMAT_GR88`), P010 as `R16` and `GR1616`,
  each layer one plane of one object, which is what the single-plane
  import takes. The mapped frame holds the VA-API frame, and the fds
  close when it is freed.
- This box's lavapipe has `VK_EXT_external_memory_dma_buf` but not
  `VK_EXT_image_drm_format_modifier`, so path A's import is Tier 2 only.
  Its Tier 1 tests cover the plan of an import (formats, layers, the
  refusals) and the copy path's fallback.

## Path A

**media.** `VideoRequest` gains `output: HwOutput` (`Download`, the
default, or `DrmPrime`). With `DrmPrime` on VA-API the decoder maps each
frame instead of downloading it: `FrameStorage::DrmPrime` keeps the
mapped `AVFrame`. `VideoFrame::dmabuf()` gives its layers (a borrowed fd,
offset, pitch, modifier, DRM fourcc, plane size); `plane()` gives
`None`, so a caller that needs bytes downloads with
`VideoFrame::to_system()` (one `av_hwframe_transfer_data` from the
mapping's source). A layer with more than one memory plane (a modifier
with DCC metadata) or an object count over one per layer is refused at
map time and the frame is downloaded instead, said once in the log and
in the frame's `transfer`. `DecodePath` stays; a new
`VideoFrame::transfer: Transfer` (`System`, `Downloaded`, `DrmPrime`)
says how the frame left the decoder. The pool grows with the frames the
cache may hold: `extra_hw_frames` is `ZERO_COPY_SURFACES` (24) with
`DrmPrime`.

**render.** `render::dmabuf` is the first GPU-side `unsafe`: the crate
goes from `forbid(unsafe_code)` to `deny(unsafe_code)` with an `allow` on
that module only (plan section 2.4's last bullet). `GpuCaps` gains
`dmabuf_import`, and `Gpu::for_window` and `headless` ask for
`VULKAN_EXTERNAL_MEMORY_DMA_BUF` when the adapter has it.
`dmabuf::import_layer` dups the layer's fd, imports it as `R8Unorm`,
`Rg8Unorm`, `R16Uint` or `Rg16Uint` with `TEXTURE_BINDING | COPY_SRC`,
and wraps it. `Uploader::upload_imported` takes the imported planes in
place of the plane bytes: an 8-bit plane is copied GPU to GPU into the
slot's level 0 (`copy_texture_to_texture`, the shown part), a deep one
goes through the ingest pass as a scratch texture does now; then the mip
chain, one submission. The slot's design is kept: the projection samples
a mip chain, which an imported image doesn't have.

As built: before the first import of a format and modifier, `Importer`
asks the driver (through ash, the version wgpu-hal uses) whether it has
that modifier for the format, in one memory plane, with sampling and
copies, importable from a DMA-BUF, and how large; wgpu-hal doesn't ask,
and an image the driver can't take is undefined behaviour, not an error.
The answer is kept. Each frame's planes are imported afresh rather than
cached by inode: wgpu tracks a wrapped texture's layout itself, so a
cached import would see no barrier when the decoder writes the surface
again, while a fresh one starts with a barrier out of `GENERAL` (wgpu is
told it starts in `COPY_SRC | RESOURCE`, which wgpu-hal maps there). An
import costs a dmabuf handle lookup and a VA mapping per plane, small
beside the copy it replaces; the bench's upload times include it, and a
cache comes back only if they show it matters.

**Keeping the surface alive.** The upload thread keeps each uploaded
`Arc<VideoFrame>` until `Queue::on_submitted_work_done` for its
submission has run, so the decoder can't reuse a surface the GPU still
reads. Ownership transfer from `VK_QUEUE_FAMILY_FOREIGN_EXT` isn't done
(wgpu has no hook for it); RADV and ANV read imported dma-bufs without
it, and the Tier 2 comparison catches a driver that doesn't.

**playback.** `PlayerConfig.zero_copy: bool`, off by default, and
`SPHERECUT_ZERO_COPY=1`. On, a VA-API stream on a device with
`dmabuf_import` decodes with `HwOutput::DrmPrime`. The frame cache caps
mapped frames at `ZERO_COPY_SURFACES − 8` (the decoder's DPB and the
frames in flight keep the rest), on top of its byte budget, which mapped
frames don't count against (they live in VRAM). Stepping back past the
cap decodes again, as a small budget does.

**What says which path a frame took.** `PerfStats` counts uploads by
path; the overlay's decoder line says `dmabuf` or `copy`; `spherecut
frame --zero-copy` (Tier 2's tool) renders through path A and its JSON
`decode` gains `"transfer": "drm_prime" | "downloaded" | "system"`
(`docs/cli-json.md`); doctor's report says whether the device can import
(`gpu.dmabuf_import`).

As built: the counters are `frames_imported` and `imports_refused`
beside `frames_uploaded`, and the overlay's line reads "into slots:
dmabuf N  vulkan N  copy N  refused N" once anything was imported,
copied out (path B, `vulkan_copies`) or refused. `PlayerSnapshot.import_refused` says why the first refusal
was; after it the stream's opens ask for downloads. The frame cache's
cap is set when the cache is made (`FrameCache::with_surface_cap`),
without its lock, since the UI thread makes the player. frame fails
with `import_failed` (exit 3) where the GPU can't import, VA-API
didn't export the frame, or the driver refuses its planes, and is a
usage error with `--reference` or a software or Vulkan decoder.
doctor's field is each Vulkan device's `dmabuf_import`
(`vulkan_devices[]`), since the device doctor reads from isn't
always the one that renders.

## Path B

*Revised 2026-10-30 before it was built, from FFmpeg 8.1.3's
`hwcontext_vulkan.c`, `vulkan.c`, `vulkan_decode.c` and
`vulkan_video.c` and wgpu-hal 30.0.1's sources.* The first design
wrapped FFmpeg's decoded image as a wgpu `NV12` or `P010` texture and
copied its planes with wgpu. Two things rule that out. A decoded picture
is in `VIDEO_DECODE_DPB_KHR` or `VIDEO_DECODE_DST_KHR`, layouts wgpu
can't name, so wgpu's first barrier would start from the wrong layout.
And when the driver lets the DPB and the output coincide (RADV does),
the picture is a reference for the pictures after it: FFmpeg's later
decodes read it, and change its layout, while the upload thread copies
it. FFmpeg orders every use of a frame through the frame's timeline
semaphore (`AVVkFrame.sem` and `sem_value`, under
`AVVulkanFramesContext.lock_frame`), and a wgpu submission can't take
part: wgpu-hal stages extra semaphores for "the next submit", which on
a device the UI also submits to may be someone else's.

So path B copies on a queue of Spherecut's own, outside wgpu, into a
buffer wgpu then reads.

**The device.** `Gpu::headless_shared` and `Gpu::for_window_shared` open
the adapter through wgpu-hal's `open_with_callback`, and wrap it with
`create_device_from_hal`. The callback adds:

- extensions: `VK_KHR_video_queue`, `VK_KHR_video_decode_queue`, and the
  device's `VK_KHR_video_decode_h264`, `_h265` and `_av1`, and
  `VK_KHR_video_maintenance1` when it has it;
- `VkPhysicalDeviceSynchronization2Features` (FFmpeg submits with
  `vkQueueSubmit2`). wgpu chains its own feature structs one by one and
  not this one, so there's no duplicate in the chain. Timeline
  semaphores wgpu enables itself. `samplerYcbcrConversion` isn't needed:
  FFmpeg's decode views are made with `VkImageViewUsageCreateInfo`
  leaving out `SAMPLED`, and nothing samples the picture;
- queues: two from a compute family other than wgpu's family 0 (index 0
  for FFmpeg, index 1 for Spherecut's copies) and one from a video-decode
  family whose operations include H.264 or H.265.

wgpu keeps family 0's queue 0, which no one else submits to. The plan of
families is a pure function of the device's queue families and
extensions, with the reason it refuses: a Vulkan device below 1.3
(FFmpeg uses 1.3's entry points), no decode family, no second compute
queue. RADV has one graphics queue, four compute ones and a decode
family. lavapipe has one queue in all, so path B refuses there, and
Tier 1 tests what can be tested without one (below). A device made so
isn't the default: the copy path's tests and the GUI keep
`Gpu::headless` and `for_window` unless path B is asked for.

**FFmpeg's side.** `media::vulkan_shared` makes an
`AV_HWDEVICE_TYPE_VULKAN` context from the device's raw handles (in
`spherecut_core::video::VkDeviceHandles`, which holds a clone of the
wgpu device so it outlives FFmpeg's context and every frame of it) and
`av_hwdevice_ctx_init`s it. ffmpeg-sys-next binds `AVVulkanDeviceContext`
and `AVVkFrame` from the headers it builds against, through a stand-in
`vulkan.h`, so their layouts follow the FFmpeg version; what changes by
version is which fields there are:

| libavutil | FFmpeg | queues given as | `AVVkFrame.access` |
|---|---|---|---|
| 58 | 6.1 | `queue_family_*_index` and `nb_*_queues` | `VkAccessFlagBits` |
| 59, 60 | 7.1, 8.1 | `qf[]`, `nb_qf` (the old fields still there) | `VkAccessFlagBits` |
| 61 | 9.0 | `qf[]`, `nb_qf` only | `VkAccessFlagBits2` |

`cfg(ffmpeg_7_1)` and a new `cfg(ffmpeg_9_0)` pick the code, and
`cargo xtask compat` builds both against 8.1.3 and 9.0.2 as it does now.
FFmpeg is given the compute family (`COMPUTE | TRANSFER`, one queue:
its frame preparation, uploads and downloads) and the decode family
(`VIDEO_DECODE`, one queue). Its frames are made `CONCURRENT` over the
families it was given, which include the copy queue's. Family 0 isn't
given, since wgpu never touches FFmpeg's images. FFmpeg's free leaves a
device it didn't make alone; the context's own free drops the handles.

**Frames.** `HwOutput::Vulkan` keeps the decoded frame
(`FrameStorage::Vulkan`), with `Transfer::Vulkan`; `plane()` is `None`
and `to_system()` downloads through FFmpeg. `VideoFrame::vulkan()` gives
a `spherecut_core::video::VkPicture`: per plane, its image and aspect
(`PLANE_0` and `PLANE_1` of one multi-planar image, or `COLOR` of an
image a plane), and, under the frame's lock, each image's layout,
access, queue family, semaphore and semaphore value.

**The copy.** `render::vkshare::Copier` owns the copy queue, a command
pool, a ring of command buffers, a timeline semaphore of its own and a
pool of device-local buffers made `CONCURRENT` over family 0 and the
copy family, each handed to wgpu (`Buffer::from_raw_managed`,
`create_buffer_from_hal`), so wgpu frees it. For a frame it:

1. locks the frame and reads each image's state;
2. records, for each image, a barrier from its layout to
   `TRANSFER_SRC_OPTIMAL` (the semaphore wait orders it after FFmpeg's
   work; the queue families stay as the frame says), then one
   `vkCmdCopyImageToBuffer` per plane, rows padded to wgpu's 256 bytes;
3. submits with a wait on each image's semaphore at its value and a
   signal at value + 1, and a signal of its own semaphore;
4. records the images' new state (`TRANSFER_SRC_OPTIMAL`, transfer read,
   value + 1) and unlocks. FFmpeg's next use of the frame, as a
   reference or a new picture, waits for the copy and leaves that layout.

The upload thread waits (on the CPU, off the UI thread) for the copy,
lets the frame go (the decoder has its surface back at once, unlike path
A), and `Uploader::upload_from_buffer` copies the buffer into the slot as
the copy path does from its staging belt: an 8-bit plane into level 0, a
deep one into its scratch texture and the ingest pass (the plane's bytes
are P010's 16-bit codes, as the copy path's are), then the mips. The
buffer goes back to the pool when wgpu is done with it
(`on_submitted_work_done`). That is one GPU copy more than a wrap would
make (an 8K NV12 picture is about 44 MB, read and written once more per frame),
and none through the CPU or PCIe.

**Order.** Path A first, through odin; then B, whose device change
touches every GPU test, on its own branch.

**Tier 1 without a second queue.** On lavapipe: the plans (families,
extensions) against RADV's, ANV's and lavapipe's families; the
refusal; `upload_from_buffer` byte-identical to the copy path for
every layout; and, in one test thread with nothing else on the device,
FFmpeg's context made on a plain wgpu device with family 0 given to it,
a frame uploaded into it by FFmpeg (`av_hwframe_transfer_data`), copied
by a `Copier` on queue 0 and uploaded, byte-identical to the copy path,
under the Khronos validation layer when it is installed. Those two
test-only steps (FFmpeg and the copier on wgpu's queue) are what
production refuses; they are `unsafe` and say so.

**As built** (branch `m1/zero-copy-b`). Where it differs from the
above:

- A wait on the CPU doesn't make the copy's writes visible to a later
  submission: under the validation layer, wgpu's copy out of the buffer
  was a read-after-write hazard on the copier's. So
  `Copier::order_before` also stages a wait on the copier's semaphore,
  at the copy's value, for wgpu's next submit
  (`Queue::add_wait_semaphore`). The worry above, that the next submit
  may be someone else's, doesn't bite: wgpu chains its submissions with
  semaphores of its own, so a wait taken by any submission orders every
  one after it, and a wait already passed costs nothing.
- FFmpeg reads the device's features itself (`ff_vk_load_props`), so
  `device_features` is an empty `VkPhysicalDeviceFeatures2`. FFmpeg 6.1
  is given the queues through its old fields (graphics none, compute,
  transfer and decode from the plan), so path B runs on 6.1 too, as the
  Tier 1 test does here; the stand-in `vulkan.h` types it binds are
  plain integers, so the fields are read and written as such.
- A frame that can't be copied as it is (cropped on the left or top, or
  in a format the copy path converts) is downloaded by the decoder, and
  its `transfer` says why, as path A's do. The frame cache counts frames
  left on a Vulkan device under the same cap as mapped ones
  (`VideoFrame::on_device`): FFmpeg's Vulkan pool grows as frames are
  held, so the cap is what bounds their video memory. The decoder's
  `extra_hw_frames` stays at 2.
- playback: with zero copy on, the app opens its device shared
  (`for_window_shared`); a Vulkan Video stream decodes through FFmpeg's
  context on it, made by the first open that wants one and kept. A
  refusal, of the context or of a frame, is kept as `import_refused` and
  turns zero copy off for the opens after, as path A's does.
  `PerfStats` counts `vulkan_copies`.
- `frame --zero-copy --decoder vulkan` renders through the copier
  (`StillRenderer::render_copied`); its JSON's `decode.transfer` is
  `"vulkan"`. On lavapipe it exits with `import_failed`: no decode
  queue to share.
- Under the validation layer (1.3.275) the Tier 1 test reports none of
  the copier's or wgpu's work. It does report FFmpeg's own uploads,
  16 times: FFmpeg's frame barriers name a multi-planar image's colour
  aspect where its copies name the planes (6.1 and 8.1 alike,
  `ff_vk_frame_barrier`), which the layer tracks apart.
- doctor doesn't say yet whether a device can be shared: that needs
  the plan in media, where render keeps it. The log and frame's
  `import_failed` say why it can't.

## Tests and measures

- Tier 1: an import's plan from a DRM descriptor (fourcc to format,
  layer and plane counts, refusals) as a pure function; the uploader's
  imported-plane path with planes made by wgpu on lavapipe (a texture
  in place of an import), byte-identical to the copy path; the cache's
  cap on mapped frames; the copy path when the device can't import, with
  the reason; `frame --zero-copy` without the feature exits with
  `import_failed` (exit 3) and says why.
- Tier 2 `zero_copy_matches_copy_path`: an X5 frame (NV12) and a 10-bit
  clip's (P010), one frame decoded by VA-API, rendered through import and
  through the copy, byte-identical. It skips, with the reason, without
  the extensions or when the driver refuses the modifier, and never
  passes then. As built it takes 48 frames of each (synthetic HEVC Main
  and Main 10, and an X5 lens when the samples are there), renders each
  through its download at once and through its import 15 frames later,
  holding the frames between as the cache would, so that a surface the
  decoder took back while held would show;
  `zero_copy_frame_matches_the_copy` runs `frame --zero-copy` against
  `--decoder vaapi`.
- Tier 2 `shared_vulkan_matches_copy_path` (path B): the same clips
  decoded by Vulkan Video on the shared device, each frame rendered
  through the copier and through `to_system()`'s download, 15 frames
  apart as above, byte-identical; it skips, with the reason, where the
  plan refuses. `shared_vulkan_frame_matches_the_copy` runs
  `frame --zero-copy --decoder vulkan` against `--decoder vulkan`.
- Tier 2 `bench_x5_8k30_zero_copy_vs_copy`: X5 8K30 playback (and each
  X5 mode) through VA-API with the copy, VA-API with import, Vulkan Video
  with the copy, and (path B) Vulkan Video shared: decoded fps, upload
  ms p50 and p99, drops. Rows into `docs/perf.md` and the H1 report.
- The decision before M3 takes these rows from odin and huginn.
